# Architecture

This document describes how checkout-sentinel v0.1 is put together, why, and where it is
expected to change as it grows into a hosted service.

## Components

```mermaid

  subgraph packages
    core["@checkout-sentinel/core<br/>journey engine, detection, schemas"]
    db["@checkout-sentinel/db<br/>Drizzle schema, migrations, repositories"]
    jobs["@checkout-sentinel/jobs<br/>queue name, job payload, schedulers"]
  end
  subgraph apps
    cli["apps/cli"]
    api["apps/api (NestJS)"]
    worker["apps/worker (BullMQ)"]
  end
  fixtures["test/fixtures<br/>local fixture stores, test helpers"]

  cli --> core
  api --> core
  api --> db
  api --> jobs
  worker --> core
  worker --> db
  worker --> jobs
  fixtures -. tests only .-> core
```

| Package / app   | Responsibility                                                                                                                                                                                                                                                                                                                 | Depends on                   |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------- |
| `packages/core` | Runs journeys with Playwright. Owns the result schema (zod, `RESULT_SCHEMA_VERSION = 1`), the monitor schema shared by the CLI config and the API, platform detection, selectors, cart reading, the order guard and the SSRF guard (address classifier, `TargetGuard`, egress proxy). Has no knowledge of databases or queues. | playwright, zod, cron-parser |
| `packages/db`   | Postgres tables, SQL migrations generated by drizzle-kit, and repositories (`MonitorRepository`, `RunRepository`, `StateRepository`, `AlertDeliveryRepository`).                                                                                                                                                               | drizzle-orm, pg              |
| `packages/jobs` | The queue contract between API and worker: queue name, job payload schema, scheduler ids, default job options and `JourneyScheduler`.                                                                                                                                                                                          | bullmq, ioredis              |
| `apps/cli`      | Human and JSON output, YAML config, exit codes. Runs journeys in process.                                                                                                                                                                                                                                                      | core                         |
| `apps/api`      | REST API, validation (including the input-time SSRF check), OpenAPI, auth, schedule reconciliation, migrations on boot, API metrics.                                                                                                                                                                                           | core, db, jobs, NestJS       |
| `apps/worker`   | Executes jobs: store lock, browser pool, journey (with the use-time SSRF check), persistence, alert state machine, guarded delivery, worker metrics. Housekeeping: stale-run sweep and retention.                                                                                                                              | core, db, jobs               |
| `test/fixtures` | Shopify-like and WooCommerce-like Express stores with broken variants, a webhook receiver and Postgres/Redis probes for e2e tests.                                                                                                                                                                                             | express, pg, ioredis         |

The boundary that matters most is `core`. It takes options and returns a `RunResult`; it can be
embedded in a CLI, a worker, a serverless function or a future Shopify app without change.

## Data model

```mermaid
erDiagram
  monitors ||--o| monitor_state : "has"
  monitors ||--o{ runs : "has"
  monitors ||--o{ alert_deliveries : "has"
  runs ||--o{ alert_deliveries : "caused"

  monitors {
    uuid id PK
    text name
    text url
    enum platform "auto | shopify | woocommerce"
    jsonb devices "[desktop, mobile]"
    text schedule "cron"
    text timezone
    int slow_step_ms
    int alert_after_failures
    jsonb alerts "webhook / slack channels"
    bool enabled
  }
  runs {
    uuid id PK
    uuid monitor_id FK
    enum trigger "schedule | manual"
    text job_id "BullMQ job of this attempt"
    enum status "running | passed | failed | error"
    timestamptz started_at
    int duration_ms
    text failed_step
    jsonb result "RunResult v1"
  }
  monitor_state {
    uuid monitor_id PK
    enum health "unknown | passing | failing"
    int consecutive_failures
    jsonb slow_steps "device:step keys over threshold"
    uuid last_run_id
    enum last_run_status
  }
  alert_deliveries {
    uuid id PK
    uuid run_id FK
    enum kind "failure | recovery | slow"
    int channel_index
    enum status "pending | sent | failed"
  }
```

Notes:

- `runs.result` stores the whole `RunResult` as JSONB. The columns next to it (`status`,
  `failed_step`, `duration_ms`, `detected_platform`) exist so list views never parse JSON.
  `(monitor_id, started_at desc)` is indexed and history uses keyset pagination on `started_at`.
- `monitor_state` is one row per monitor. It is both the memory of the alerting state machine and
  the "latest status" read model, so `GET /monitors` is a single join.
- `alert_deliveries` has a unique index on `(run_id, kind, channel_index)`. The worker inserts the
  row before sending; if the insert conflicts, the alert was already handled.
- All foreign keys cascade on monitor delete.

## Job flow

```mermaid
sequenceDiagram
  participant C as Client
  participant A as API
  participant P as Postgres
  participant R as Redis (BullMQ)
  participant W as Worker
  participant S as Store
  participant H as Webhook / Slack

  C->>A: POST /monitors
  A->>P: insert monitor + monitor_state
  A->>R: upsertJobScheduler("monitor:<id>", cron, tz)
  Note over R: BullMQ creates the next delayed job from the cron
  R->>W: journey job {monitorId, trigger}
  W->>P: load monitor
  W->>R: SET store-lock:<host>:<slot> NX PX
  alt store busy
    W->>R: moveToDelayed(now + 15-30s)
  else lock acquired
    W->>P: insert run (running)
    W->>S: Chromium context per device: product, add to cart, cart, checkout
    W->>P: update run with RunResult
    W->>P: SELECT monitor_state FOR UPDATE, apply transition
    opt state changed
      W->>P: claim alert_deliveries row
      W->>H: POST alert
      W->>P: mark sent / failed
    end
    W->>R: release store lock
  end
```

Schedules live in two places: Postgres is the source of truth, and BullMQ holds one job scheduler
per enabled monitor. The API writes both on create, update and delete, and on every boot it
re-upserts all schedulers and removes orphans. If Redis is flushed or a write between the two
stores fails, a restart of the API repairs it.

## Alert state machine

```mermaid
stateDiagram-v2
  [*] --> unknown
  unknown --> passing: passed
  unknown --> failing: N consecutive failed (alert: failure)
  passing --> failing: N consecutive failed (alert: failure)
  failing --> passing: passed (alert: recovery)
  failing --> failing: failed (no alert)
  passing --> passing: passed (alert: slow, for newly slow steps only)
```

`N` is the monitor's `alertAfterFailures`. Runs with status `error` leave the state untouched:
they describe our infrastructure, not the store. The transition function is pure
(`apps/worker/src/alerting/state-machine.ts`) and covered by unit tests; it is applied inside a
transaction holding a row lock on `monitor_state`, so two runs finishing together cannot both
alert.

## Housekeeping: stuck runs and retention

Each worker tries a housekeeping pass when it starts and then every `HOUSEKEEPING_INTERVAL_MS`
(default 5 minutes; `0` turns it off on that worker). A Redis lock (`checkout-sentinel:housekeeping`,
`SET NX PX` with a 5 minute TTL and a compare-and-delete release) lets one pass run at a time
across all workers; a worker that finds the lock taken skips that pass. A pass runs two tasks in
this order. A failure in one is logged and counted, and does not stop the other. The code is in
`apps/worker/src/housekeeping.ts` and the queries in `RunRepository`.

**Stale-run sweep.** A worker that dies mid-run leaves its run row in `running`. BullMQ sees the
job's lock expire and usually runs the job again, and the new attempt marks the old row lost
when it starts (see below). When BullMQ does not run the job again, for example because it
stalled too often, nothing else would finish the row. The sweep marks every run still `running`
`RUN_STALE_AFTER_MS` after it started as `error`, with
`Worker lost: the run was still running 15 min after it started`. It compares `started_at` with
the database clock, so the workers' clocks do not matter.

Without `RUN_STALE_AFTER_MS` the threshold is 15 minutes, or the worker's estimate of its
longest run when that is longer: 2 devices × 6 steps × (`NAVIGATION_TIMEOUT_MS` +
`STEP_TIMEOUT_MS`) + 2 minutes, which is 11 minutes with the default timeouts. The estimate is
not a hard bound, which is why the default keeps a margin above it. A worker logs a warning at
start when `RUN_STALE_AFTER_MS` is set below the estimate. Give every worker the same timeouts
and threshold: the worker that sweeps applies its own.

The sweep never changes `monitor_state`. Like every `error` run, a swept run says nothing about
the store: health, the failure count, slow steps and the last run stay as they were, and no alert
is sent.

**A result that arrives late.** A worker can be slow rather than dead, for example after a long
pause, or when it lost Redis but not Postgres. It stops renewing its BullMQ job lock, BullMQ
declares the job stalled and runs it again on another worker, and then the original journey
finishes. The rule is that a run's final status is written once, and an attempt that BullMQ has
given up on never applies its result:

- Each run records the BullMQ job it is an attempt of (`runs.job_id`). When an attempt starts
  its run, the same transaction marks the job's earlier runs that are still `running` as
  `error`, with `Worker lost: BullMQ ran the job again before this run finished`. This does not
  wait for the sweep. With `PER_STORE_CONCURRENCY=1` the new attempt waits for the store lock
  first, so it starts once the stalled attempt finishes or its store lock expires (10 minutes).
- A result is stored and applied to `monitor_state` in one transaction
  (`StateRepository.applyRunResult`), and only while the run is still `running`.
  `RunRepository.fail` also changes only a run that is still `running`. The sweep, a new attempt
  and a finishing worker cannot both win: they update the same row, so one waits for the other
  and then finds the row no longer `running`. The sweep skips rows that a finishing worker holds
  locked (`FOR UPDATE SKIP LOCKED`).
- A late result is discarded. The run stays `error` ("Worker lost"), the result is not stored,
  the state machine does not see it and no alert is sent. The worker logs a warning and counts it
  in `checkout_sentinel_discarded_results_total`. Applying it could move the state backwards:
  the new attempt may already have applied a newer result.
- What BullMQ records for the late attempt depends on whether its worker still holds the job.
  After a stall the job belongs to the new attempt: BullMQ refuses the old worker's completion
  (`Missing lock` or `Lock mismatch`, logged as `worker error`) and keeps the new attempt's
  outcome. The outcome `discarded` is recorded only when the same worker still held the job,
  which means a live run that outlived `RUN_STALE_AFTER_MS` and was swept.
- Every attempt starts its own run row, so the newest attempt's result is applied as usual.

`apps/worker/test/e2e/housekeeping.e2e.test.ts` covers both cases with real journeys: a run swept
while it is in progress, and a stalled attempt that a second worker runs again, whose older
result arrives after the new attempt applied its own and before any sweep.

**Retention.** Runs that started more than `RUN_RETENTION_DAYS` ago (default 30, database
clock) are deleted in batches of 500, oldest first, at most 20 batches per pass; the rest waits for
the next pass. `0` keeps run history forever. A run's alert deliveries are deleted with it
(foreign key cascade). These runs are kept whatever their age:

- each monitor's latest run, so its history is never empty;
- the run `monitor_state.last_run_id` points at;
- the run behind each monitor's latest alert of each kind (failure, recovery, slow), so the
  delivery rows of the current state stay. The failure alert of an incident that is still open
  stays in `GET /monitors/:id/alerts`, however long the incident lasts;
- runs still `running`. The sweep runs first and finishes the stale ones.

After deleting rows, the pass removes each deleted run's artifact directory
(`<ARTIFACTS_DIR>/<monitorId>/<runId>/`) and the directories of monitors that no longer exist
(deleting a monitor through the API deletes its runs at once). Only directories named with a UUID
are touched. Rows go first: if the worker stops in between, files stay behind, never rows that
point at missing files. Files are removed from the disk of the worker that runs the pass, so
workers need one shared artifacts volume, as in the compose stack, for retention to reach every
file.

Two indexes keep a pass cheap: a partial index on `runs (started_at) where status = 'running'`
for the sweep, and `runs (started_at)` for retention.

**Metrics** on each worker's `/metrics`: `checkout_sentinel_runs_swept_total`,
`checkout_sentinel_runs_superseded_total` (runs marked lost by a new attempt of their job),
`checkout_sentinel_discarded_results_total`, `checkout_sentinel_runs_deleted_total`,
`checkout_sentinel_artifact_dirs_deleted_total` and
`checkout_sentinel_housekeeping_failures_total{task}` (`sweep`, `retention`, `artifacts`,
`pass`). Each counts on the worker that did the work, so sum them across workers.

## Outbound requests and SSRF

Every URL the system fetches for a user (product pages, webhooks, Slack) goes through one
policy, `TargetGuard` in `packages/core/src/ssrf.ts`. It is checked twice: when the API accepts
the URL, and when the worker uses it, because DNS can change in between.

```mermaid
flowchart LR
  client([Client]) -->|POST/PATCH /monitors| api[API]
  api -->|checkUrl: rules + DNS| guard{{TargetGuard}}
  worker[Worker] -->|before each run: checkUrl| guard
  worker --> browser[Chromium context]
  browser -->|all traffic, per-run proxy| proxy[Egress proxy<br/>127.0.0.1]
  proxy -->|lookup: resolve, check,<br/>connect to checked address| store[(Store)]
  worker -->|alert: lookup pinned,<br/>no redirects| hooks[Webhook / Slack]
```

- **Rules.** http or https only, no credentials in the URL, ports 80 and 443 unless allowed,
  Slack channels on `https://hooks.slack.com/` only, and no host that is, or resolves to, a
  loopback, private, CGNAT, link-local, unique-local, IPv4-mapped, multicast, unspecified or
  reserved address. The classifier parses IPv4 the way the WHATWG URL parser does, so decimal,
  octal and hex forms cannot slip past it. A refusal for a name never includes the address it
  resolved to, since reasons reach API clients and stored results; the guard's `onDnsRefusal`
  hook hands that address to a debug log in the API and worker. The egress proxy reports
  connection failures by kind, not with the raw socket error.
- **Input time.** The API runs the full check, DNS included, after schema validation and
  answers 400 with one issue per refused URL. A name that does not resolve is accepted; it is
  checked again before use.
- **Use time, journey.** `runJourneys` checks the product URL first and returns status `error`
  when it is refused. Then, unless private targets are allowed, it starts an `EgressProxy` on
  127.0.0.1 for the run and gives each browser context `proxy: { server }`. Playwright's route
  handlers are not called for redirect hops, so routing cannot stop a redirect to an internal
  host; the proxy sees every connection, redirect hops and cart API reads included. HTTPS is
  tunnelled with `CONNECT`, so the browser's own TLS reaches the store. Refused connections are
  recorded per step and listed in the step's `details.blockedRequests`. A failed step's message
  names a refused or failed connection only when it can be the cause: a main-frame navigation
  or redirect hop during that step, or the store's own host and port. A refused image, script
  or frame does not fail a step and does not change its message.
- **Use time, alerts.** Deliveries use `node:http`/`node:https` with the guard's `lookup`, a
  fresh connection each time and no redirect following.
- **Pinning.** The proxy and alert deliveries pass `TargetGuard.lookup` to the socket. It
  resolves the name, refuses the answer if any address is not public, and hands the socket
  only the addresses it checked. A short-TTL name cannot pass the check with one answer and
  connect with another.
- **Opt-in for development.** `ALLOW_PRIVATE_TARGETS=true` skips the address, port and Slack
  checks, and no proxy is started. The fixture tests use it. `ALLOWED_TARGET_HOSTS` and
  `ALLOWED_TARGET_PORTS` are narrower exceptions for production. The CLI runs without a guard
  unless `--block-private-targets` is passed; with it, the CLI builds the guard from the same
  two exception settings and never from `ALLOW_PRIVATE_TARGETS`.

## Failure handling

| Failure                                          | Behavior                                                                                                                                                                                                                                                                                                          |
| ------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A journey step fails                             | A normal result: run stored as `failed`, state machine decides about alerts. The job succeeds.                                                                                                                                                                                                                    |
| Chromium fails to launch or crashes mid-run      | `runJourneys` returns status `error` with the message; no alert. The browser pool drops a disconnected browser and launches a new one on the next job.                                                                                                                                                            |
| Exception in the worker (database down, bug)     | The run is marked `error` if it is still `running`, the job throws, BullMQ retries once after 30 seconds (exponential backoff). The retry is a new run; if marking the old run failed too, the retry marks it `Worker lost` when it starts.                                                                       |
| Worker killed mid-job                            | BullMQ's lock expires and the job is picked up again as stalled, as a new run, which marks the orphaned row `error` (`Worker lost: ...`) when it starts. If BullMQ does not run the job again, the sweep marks the row `RUN_STALE_AFTER_MS` after it started. Health and alerts are not affected.                 |
| Worker paused, finishes after a retry or sweep   | The late result is discarded: the run stays `Worker lost`, no state change, no alert. If BullMQ ran the job again, it refuses the late completion and keeps the new attempt's outcome; job outcome `discarded` appears only when the paused worker still held the job. The new attempt's run is applied as usual. |
| Housekeeping pass fails (database or Redis down) | Logged and counted in `checkout_sentinel_housekeeping_failures_total`; the next pass tries again. If a worker dies mid-pass, the lock frees itself after its 5 minute TTL.                                                                                                                                        |
| Store busy (another run holds its lock)          | Job moved back to delayed with 15 to 30 seconds of jitter. Not counted as an attempt.                                                                                                                                                                                                                             |
| Alert endpoint down                              | Two attempts per delivery (retrying network errors and 5xx, not 4xx), then recorded as `failed` in `alert_deliveries` and counted in metrics. The run itself is not retried.                                                                                                                                      |
| Job retried after alerts were sent               | The unique delivery key makes the second send a no-op.                                                                                                                                                                                                                                                            |
| Monitor URL refused at use time                  | The URL is private now (DNS changed, or the monitor predates the guard): run stored as `error` with `Target blocked: ...`; no state change, no alert.                                                                                                                                                             |
| Page redirects or loads from a private host      | The egress proxy refuses the connection. A navigation fails the step with `Blocked a request to ...`; a refused subresource is only listed in `details.blockedRequests`.                                                                                                                                          |
| Alert URL refused at send time                   | Recorded as `failed` with `Blocked: ...` and counted in metrics; not retried. A 3xx answer is also final: deliveries never follow redirects.                                                                                                                                                                      |
| SIGTERM                                          | The worker stops taking jobs and starting housekeeping passes, waits for running journeys and a pass in progress (compose gives it 90 seconds), then closes Chromium, Redis and Postgres. The API stops accepting connections, then closes its pools.                                                             |
| Concurrent API boots                             | Migrations run under a Postgres advisory lock.                                                                                                                                                                                                                                                                    |

## Scaling notes

**Horizontal workers.** Workers are stateless apart from their Chromium process. Add replicas
(`docker compose up --scale worker=N`, or a Deployment in Kubernetes) and BullMQ distributes jobs.
Each worker runs `WORKER_CONCURRENCY` journeys in parallel. A journey holds one browser context,
so memory, not CPU, is usually the limit; size workers by measuring a representative store
rather than by a fixed rule.

**Per-store concurrency.** Adding workers must not mean hitting one merchant harder. The store lock
is a set of `PER_STORE_CONCURRENCY` Redis keys per host (`SET NX PX` with a 10 minute TTL and a
compare-and-delete release), shared by every worker. A job that cannot get a slot is delayed, not
failed. In a hosted version this becomes a per-plan limit, and many monitors on one host would
also be spread across the schedule.

**Browser pool.** v0.1 keeps one Chromium per worker process, reused by all its jobs, with a fresh
context per journey. That is the main cost saving over launching Chromium per run, and contexts
give full isolation of cookies and carts. Next steps if needed: recycle the browser after N
journeys to cap memory growth, and move to a pool of several browsers per process, or to a remote
browser service, when one process saturates.

**Queue and database.** Run history grows linearly with monitors times frequency. Retention bounds
it (`RUN_RETENTION_DAYS`, see [Housekeeping](#housekeeping-stuck-runs-and-retention)); the next
lever is partitioning `runs` by month, which would turn retention into dropping old partitions. The `result` JSONB can move to object storage with only a pointer
kept in Postgres. Redis holds only queue state; completed and failed jobs are trimmed by count and
age.

**Multi-tenancy (hosted SaaS).** The current schema has no tenant column. The planned path is an
`accounts` table, `account_id` on `monitors`, row-level filtering in the repositories and
per-account API keys replacing the single `API_TOKEN`. The SSRF guard described above is already
in place and on by default, which a hosted version needs before untrusted users can create
monitors.

**Egress proxy.** One proxy per run, in the worker process, adds one local hop per connection.
It holds no state beyond the run's event list, so it scales with the worker.

## Decisions

- **Drizzle over Prisma**: SQL-first migrations that are plain files in the repo, no generated
  client or engine binary in the Docker images.
- **zod everywhere**: one schema validates the CLI config, the API body (through NestJS 12's
  Standard Schema pipe) and generates the OpenAPI document, so they cannot drift.
- **Explicit DI tokens in NestJS**: providers are injected with `@Inject(TOKEN)`, so DI does not
  depend on emitted decorator metadata and the tests can run through Vitest's transformer.
- **Egress proxy over Playwright routing for SSRF**: route handlers do not see redirect hops,
  and checking a name in Node while Chromium resolves it again leaves a DNS rebinding window.
  A per-context proxy that connects to the address it checked closes both, and covers frames,
  subresources and the context's request client without extra code.
- **Workspace source condition**: packages export a `@checkout-sentinel/source` condition pointing
  at `src/`. Typecheck and tests use it, so they never need a prior build; Node at runtime and the
  production build use `dist/`.
